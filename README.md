# internet-speed-meter

[![CI](https://github.com/r-1805/internet-speed-meter/actions/workflows/ci.yml/badge.svg)](https://github.com/r-1805/internet-speed-meter/actions/workflows/ci.yml)

Скрипт замеряет скорость интернета со своего компьютера. Он принимает адрес тяжёлого файла
(например, большой картинки), последовательно выполняет 10 запросов, каждый раз скачивает
ответ целиком и печатает среднее время запроса, объём скачанных данных и скорость в Мбит/с.

Зависимостей нет, только стандартная библиотека Python.

## Требования

Python 3.9 или новее. Проверить версию: `python --version` (на Windows может понадобиться `py`).

## Установка и запуск

```bash
git clone https://github.com/r-1805/internet-speed-meter.git
cd internet-speed-meter
python speed_meter.py https://upload.wikimedia.org/wikipedia/commons/3/3f/Fronalpstock_big.jpg
```

Другой адрес для проверки: тестовый файл Cloudflare на 25 МБ. Кавычки нужны из-за `?` в адресе.

```bash
python speed_meter.py "https://speed.cloudflare.com/__down?bytes=25000000"
```

Если сервер начал отвечать `HTTP 429 Too Many Requests`, значит, он ограничил частые
скачивания. Подождите несколько минут или возьмите другой адрес.

### Параметры

| Параметр | По умолчанию | Описание |
|---|---|---|
| `url` | обязательный | Адрес файла, `http://` или `https://`. Кириллица и пробелы кодируются автоматически |
| `-n`, `--requests` | `10` | Сколько запросов выполнить |
| `-t`, `--timeout` | `30` | Сколько секунд ждать данных от сервера |
| `--json` | выключен | Вывести результат в JSON |

Справка: `python speed_meter.py --help`.

Если запрос не удался, скрипт пишет причину и переходит к следующему:

```

```

По Ctrl+C скрипт останавливается и печатает итог по уже выполненным запросам.

### Коды выхода

| Код | Значение |
|---|---|
| `0` | Хотя бы один запрос успешен |
| `1` | Ни один запрос не выполнился |
| `2` | Неверные аргументы |
| `130` | Прервано через Ctrl+C |
| `141` | Получатель вывода закрылся раньше времени, например `\| head -3` |

## Обработка ошибок

Ошибка одного запроса не останавливает замер: скрипт пишет причину, переходит к следующему
запросу и не учитывает неудачный в средних. Повторных попыток нет намеренно: иначе
нестабильное соединение выглядело бы стабильным.

| Сообщение | Причина | Что делать |
|---|---|---|
| `HTTP 403` | Сервер не отдаёт файл скриптам | Взять другой адрес |
| `HTTP 404` | Файла нет по этому адресу | Проверить ссылку |
| `HTTP 429` | Слишком частые скачивания | Подождать несколько минут или сменить адрес |
| `HTTP 5xx` | Ошибка на стороне сервера | Повторить позже или сменить адрес |
| `не удалось найти хост (DNS)` | Опечатка в домене или нет интернета | Проверить адрес и подключение |
| `сервер отклонил соединение` | На этом порту ничего не слушает | Проверить адрес и порт |
| `тайм-аут` | Сервер не отвечает дольше `-t` секунд | Увеличить `-t`, проверить прокси и файрвол |
| `сервер закрыл соединение, не отправив ответ`, `сервер сбросил соединение`, `соединение оборвалось` | Обрыв связи или сервер прервал отдачу | Повторить замер; если повторяется, сменить адрес |
| `не прошла проверка SSL-сертификата` | Сертификат сайта недействителен, либо в системе нет корневых сертификатов | На macOS с Python с python.org запустить `Install Certificates.command` из папки Python |

Если ответ в среднем меньше 1 МБ, в конце выводится предупреждение: на таком объёме скорость
неточная, а адрес часто ведёт на HTML-страницу вместо файла. Например, страница файла в
Википедии вместо прямой ссылки на картинку.

Прокси из переменных окружения `HTTP_PROXY` и `HTTPS_PROXY` учитываются автоматически.

Неверные аргументы (адрес без `http://`, `-n 0`, `-t abc`) проверяются до начала замера,
скрипт завершается с кодом 2 и сообщением, что именно не так. Ошибка в самом скрипте не
скрывается и выводится с трейсбеком, чтобы её можно было найти.

## Как считаются метрики

Каждый запрос делится на две части: ожидание ответа (DNS, TCP/TLS, обработка на сервере) и
скачивание тела.

- Время запроса: от начала запроса до последнего байта тела, обе части вместе.
- До первого байта (TTFB): через сколько пришли заголовки ответа.
- Скорость скачивания = скачанные байты / время скачивания тела, без ожидания ответа. Это
  пропускная способность канала, основная метрика.
- С учётом ожидания ответа = скачанные байты / полное время запроса. Эта цифра ниже и
  сильнее зависит от размера файла: на маленьком файле ожидание ответа занимает большую
  долю времени. На файле Cloudflare 5 МБ разница была почти вдвое, 88 и 159 Мбит/с.

Итоговые скорости считаются как сумма байтов, делённая на сумму времени по всем успешным
запросам. Среднее скоростей отдельных запросов не используется, потому что один случайно
быстрый запрос завысил бы результат.

1 МБ = 1 000 000 байт, 1 МБ/с = 8 Мбит/с. Провайдеры указывают скорость в Мбит/с.

Неудачные запросы не входят в средние, но учитываются в строке «Успешных запросов».

### JSON

`--json` выводит список запросов, итог и предупреждения. Время в секундах, размер в байтах,
скорость в Мбит/с. Если ни один запрос не прошёл, метрики итога равны `null`, а не `0`:
«нет данных» и «скорость ноль» — разные ситуации.

```json
{
  "url": "https://...",
  "requests": [
    {"number": 1, "elapsed": 1.771, "ttfb": 0.427, "size": 14679474, "error": null}
  ],
  "summary": {
    "total": 10, "succeeded": 10, "total_bytes": 146794740,
    "avg_time": 1.646, "avg_ttfb": 0.378,
    "download_speed_mbit_s": 92.59, "request_speed_mbit_s": 71.33
  },
  "warnings": []
}
```

## Ограничения

- Скорость меряется до конкретного сервера. На одном и том же канале Wikimedia дала
  92 Мбит/с, а Cloudflare 332 Мбит/с. Для оценки канала берите файл от 10 МБ на быстром CDN
  и сравнивайте несколько серверов.
- Каждый запрос открывает новое соединение, поэтому в «С учётом ожидания ответа» каждый раз
  входит TCP/TLS-рукопожатие.
- Редиректы выполняются автоматически, их время входит в ожидание ответа.
- Тайм-аут считается на каждую операцию чтения, а не на весь запрос. Сервер, который отдаёт
  данные медленно, но без пауз дольше тайм-аута, не прервётся.
- Если сервер закрыл соединение раньше, чем отдал весь ответ, запрос считается ошибкой.

## Разработка

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt

pytest          # тесты поднимают локальный HTTP-сервер, интернет не нужен
ruff check .
ruff format .
```

GitHub Actions на каждый push запускает ruff и тесты на Ubuntu и Windows с Python 3.9 и 3.13.

## Как использовался AI

Код написан с Claude Code. Результат проверялся тестами, ручными прогонами на реальных
серверах и отдельным ревью. Что нашлось и было исправлено, видно в истории коммитов:

- Первая версия засчитывала обрезанный ответ как успешный: `http.client` при чтении кусками
  не бросает `IncompleteRead`, если сервер закрыл соединение раньше времени. Ошибку поймал
  тест ещё до первого коммита, исправлено сверкой с `Content-Length`.
- URL с кириллицей и некорректный URL (`http://[::1`) приводили к падению с трейсбеком.
- Перенаправление вывода в файл на Windows с кодовой страницей cp1252 падало на первой
  русской строке.
- Ctrl+C терял все уже сделанные замеры.
- `| head` приводил к падению с трейсбеком. Ответ на 1 КБ (HTML-страница вместо файла)
  выдавал скорость как нормальный результат. Сообщения об ошибках SSL и обрыве соединения
  были сырыми английскими текстами исключений.
- Обработчик ошибок сам падал на `SSLError` без атрибута `reason`. Теперь тест перебирает все
  подклассы сетевых исключений и проверяет, что обработчик на них не падает.
- Скорость считалась по полному времени запроса вместе с ожиданием ответа сервера, из-за
  этого занижалась и зависела от размера файла. Теперь это две отдельные метрики.
- Заголовки `Cache-Control: no-cache` и `Pragma` добавлялись «на всякий случай». Проверка
  показала, что Wikimedia всё равно отдаёт файл из кэша, а отдача с ближайшего узла CDN — это
  и есть то, что нужно измерять. Заголовки убраны.
